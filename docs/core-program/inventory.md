# Инвентаризация Fokus: каталог, планировщики, адаптация

Срез: `main` = `1239933` (12.11.2026). Метод: статический разбор `src/` плюс динамический прогон каждого модуля
из `registry` в jsdom (`scripts/inventory/probe.inv.ts`, запуск `npm run inventory`). Каждый модуль рендерится на
уровне 1 и на максимальном уровне при детерминированном `Math.random` (seed). 240 с пользователь ничего не нажимает,
затем `isTimeUp()` становится `true`, затем вызывается cleanup. Так мерим, когда блок заканчивается сам, какой
результат он отдаёт без ввода, остаются ли таймеры и обработчики после cleanup и воспроизводим ли первый экран
при одном seed.

## Главное

1. **181 упражнение** в `registry.ts` (attention 48, memory 44, flexibility 35, logic 33, speed 21). Явная структура
   `manifest/engine/view` есть у 35 модулей, остальные 146 — один файл, где генерация, оценка и DOM смешаны.
   Тесты упоминают только 49 модулей.
2. **У 161 из 181 нет таблицы уровней в манифесте**: сложность считается формулой внутри view. Ещё у 3
   (`corsi`, `posner`, `math-sprint`) `levels: {}`, и только у 17 таблица есть. Каталог движка (`catalogFromManifests`) при этом считает
   `maxLevel = 20` или `5`, то есть движок выбирает сложность, которую упражнение толкует по-своему.
   У `n-back` таблица в манифесте (9 уровней) расходится с реально используемой `getNBackParams`.
3. **Четыре генератора зависают навсегда** (бесконечный `while` → вкладка висит): `avatar-names` уже на уровне 1–2,
   `word-pairs`, `shape-count` (ответ 0 или 1), `dot-span` (уровень > 14). Любой планировщик может их выбрать.
4. **Блоки не ограничены по времени.** Session задаёт `blockTimeLeft = timeLeft` (весь остаток сессии), а
   168 из 181 модулей сами не заканчиваются (139 ждут ответа, 29 тикают до конца сессии). Первое такое упражнение
   съедает весь бюджет, а «Блок 1 из 3» на экране неправда. Сами по себе через ~70 с заканчиваются только 9 модулей
   (`stroop`, `switch-rule`, `odd-one`, `pattern-next`, `shape-equation`, `dominant-color`, `vowel-count`,
   `go-no-go` за 26 с, `verbal-fluency` за 1 с).
5. **Фон и пауза создают ложные результаты.** Ни session, ни упражнения не слушают `visibilitychange`.
   Кнопка «Пауза» останавливает только таймер сессии: таймауты проб внутри упражнения продолжают идти и
   записываются как промахи. Без ввода 8 модулей отдают точность > 25 % (`verbal-fluency` 100 %, `beacon-rail`
   и `digit-filter` 74 %, `vigil-probe` 64 %, `n-back` 52 %, `zone-guard` 47 %, `ay-color-pulse` 40 %,
   `pulse-rail` 38 %). Пользователь отошёл, а результат «хороший».
6. **Форма результата одна** (`{accuracy, avgRtMs, rounds}`), но смысл разный: 9 модулей отдают `rounds = 0`
   при `avgRtMs > 0`; у `arcade-shooter` `metricModel` — объект; 5 модулей зовут `onEnd` дважды
   (`zone-guard`, `spark-lane`, `tide-gate`, `slip-mark`, `cut-bar`; от рекурсии спасает только `blockEnded` в session);
   `arcade-shooter` падает без canvas-контекста и не возвращает cleanup.
7. **Cleanup.** 5 модулей оставляют по 2 обработчика `document` после cleanup (`grid-memory`, `number-sort`,
   `color-shape-switch`, `find-pair`, `missing-operator`). `n-back` не отменяет `speechSynthesis` и отложенный
   `setTimeout(startRound)`. Общий `stage.ts` закрашивает фидбек только зелёным и красным.
8. **Три планировщика показывают и играют разные планы.** «Сегодня» рисует план `ritual-targeter.targetRitual`
   (через `describeAdaptiveDepth`) поверх плана `planWithRecovery → planForNow → engine/ritual.composeRitual`.
   Session с блока 2 перепланирует заново через `planWithRecovery`. Пользователь видит одни упражнения, «почему»
   объясняет второй план, а играется третий.
9. **Аналитика выдаёт эвристику за вероятность.** После одной калибровки и одной сессии экран «Статистика»
   пишет «5 из 5 областей · Уверенность 60 %», «Специализированный профиль», «личный рекорд · 263»
   (скриншот `screenshots/before/08-progress.png`). `confidence = 60 % × охват доменов + 40 % × min(1, освоено/10)`
   не вероятность. Индекс — среднее доменов, поэтому смена состава упражнений двигает его как «рост».
10. **Иконки.** В `public/art` 91 иконка на 181 упражнение. Для ~95 упражнений Today, Session, Program и Progress
    показывают битую картинку (например «Анаграммы» на `screenshots/before/04-today.png`).
11. **Длительность по умолчанию расходится**: `storage` 900 с, `adaptive-plan` 900, `program.ts` 900,
    а миграция `offline-sync`, `privacy`, `progress` и `result` берут 300. Онбординг предлагает 5/8/12 минут.
12. **Стартовая загрузка**: registry импортируется статически, поэтому все 182 чанка упражнений попадают
    в modulepreload (подробности в `perf-baseline.md`).

## Непонятные инструкции

- Слишком коротко или двусмысленно: `stroop` «Нажми на слово, подходящее по цвету» (по цвету чернил или по смыслу?),
  `switch-rule` «Смотри на подпись. Да или нет. Правило меняется.», `pulley` «Подвесь ровно столько, сколько нужно
  двери…», `swings` «Прыгай на перекладину. Мимо — сначала.», `odd-one` «Найди элемент, который отличается»
  (по какому признаку?).
- Инструкция про клавиатуру, а на телефоне клавиш нет (15 модулей): «ПРОБЕЛ», «(Влево)/(Вправо)», «Вверх — Зима…».
- Правило задаётся только цветом (19 модулей): «СИНЯЯ рамка — сложите», «ЗЕЛЁНАЯ стрелка — туда», «КРАСНАЯ кнопка
  на ЗЕЛЁНЫЙ круг». Для людей с нарушением цветовосприятия это не работает. Обычно нужен второй носитель:
  форма, подпись или иконка.
- `n-back` требует слух (буквы диктует синтез речи), беззвучной альтернативы нет. `verbal-fluency` требует
  распознавания речи и без него засчитывает 100 %.
- Session показывает одну и ту же инструкцию каждый раз; короткой пробы перед первым зачётным запуском нет.

## Проблемы уровней

- Таблица уровней есть у 17 модулей, у остальных 164 — формула внутри view, не проверяемая тестами.
- `n-back`: таблица из 9 уровней в манифесте не используется. Реальная `getNBackParams` на уровне 4 даёт n = 2 и
  delay 3500 мс, на уровне 3 — n = 1 и delay 2000 мс: после повышения уровня темп становится медленнее.
- `catalogFromManifests` для модулей без таблицы задаёт `maxLevel = 20`, а `resolveLevelIndex` у модулей
  с таблицей зажимает по своей длине. «Сложность 12» значит разное у разных упражнений.
- `dot-span`: уровень выше 14 — бесконечный цикл, адаптивный `span++` доводит до того же.
- Монотонность сложности не проверяется ни для одного модуля, кроме отдельных тестов на `stroop` и `grid-memory`.
- Две системы сложности работают одновременно: `adaptive.updateExerciseState` + `spaced-difficulty`
  (сохраняются в `exerciseStates.difficulty`) и IRT-подбор `engine.selectDifficulty` (`difficultyFor` в session
  перезаписывает сложность перед каждым блоком).

## Несогласованные результаты

- Таймаут пробы модули учитывают по-разному: в `stroop` и `odd-one` RT таймаута = дедлайн, в `n-back` к RT
  прибавляется задержка только за ошибку, у модулей с запоминанием RT — это время всего ответа. Поэтому `avgRtMs`
  разных упражнений несравним, а `calculateNormalizedPerformance` их смешивает.
- `rounds = 0` при ненулевом `avgRtMs` (9 модулей): деление на ноль маскируется, в историю пишется «0 %».
- `targetMs` в session берётся из `levels[difficulty].targetMs`. У 164 модулей таблицы нет, поэтому всегда 1500 мс:
  для `schulte` это слишком быстро, для `go-no-go` слишком медленно.
- `sr.confidenceAfter = attempts/15 × 100` в session — ещё одна «уверенность» в процентах, не связанная ни с
  `fokus-index.confidence`, ни с `skill.confidence`, ни с `engine.confidencePct`.
